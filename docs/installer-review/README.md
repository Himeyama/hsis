# インストーラー構成の検討（2026-11-05）

単一 EXE でオフラインのインストールが完結する前提で、配布サイズと展開速度を検討した。今回は調査結果を記録し、インストーラーの実装は変更していない。

## 調査対象と現状

調査時点のコードは `Directory.Build.props` の 0.11.1。手元にある直近の自己インストーラー `artifacts/distribution/HSIS-0.10.5-win-x64-Setup.exe` をサイズ・展開計測の対象にした。0.11.1 を再生成した結果ではない。

| 区分 | バイト数 | MiB |
|---|---:|---:|
| 配布 EXE 全体 | 107,905,630 | 102.91 |
| WPF セットアップ実行部（.NET 同梱 bundle） | 64,141,239 | 61.17 |
| 配布データ（manifest と 7z） | 43,764,359 | 41.74 |
| 末尾情報 | 32 | — |

配布データは 437 エントリ。7z 本体は 43,716,875 バイト。元の Studio・CLI の配布フォルダーは 436 ファイル、144,735,131 バイト（138.03 MiB）で、生成時にアイコンが追加される。

すでに実施済みの削減は次のとおり。

- セットアップとアンインストーラーは同じ bundle を使い、配布 EXE には一度だけ格納する（`HSISPKG3`）。
- HSIS 自身の Studio と CLI は、分割した DLL を同じフォルダーに置き、.NET / WPF のランタイムを共用する。WPF 側の `WindowsBase.dll` を優先する現在の構成を維持する。

一方、セットアップを動かす .NET / WPF と、インストールする HSIS を動かす .NET / WPF は別々に格納される。現行 `BuildAsync` は `CreatePayloadAsync` に `runtimeDirectory` を渡しておらず、今回の manifest も共有ファイルは 0 件だった。

## 構成案

### A. セットアップと削除処理をネイティブ化する

最小化を優先する場合の本命。Studio は現在の WPF を維持し、生成する Setup / Uninstall の画面とインストール処理だけを Win32 等で実装する。小さな起動部、定義・削除情報、圧縮済み配布データを 1 本の EXE にまとめる。

起動部に LZMA2 のネイティブデコーダを組み込み、画面はすぐに表示し、インストール開始後に配布データを展開する。セットアップとアンインストーラーは同じ起動部を共用し、削除時には配布データを保持しない。

今回のデータならサイズの出発点は「約 41.74 MiB の配布データ＋新しいネイティブ実行部・削除情報」。現在の 61.17 MiB のセットアップ bundle を置き換えられる。ただし新しい実行部は未実装であり、最終サイズや総インストール時間の確定値ではない。

最大の代償は実装量と UI の変更。規約、保存先、進捗、完了、削除、ライト／ダーク、DPI、キーボード操作、アクセシビリティの実装と検証が必要。既存 `Hsis.Bootstrap` は準備画面用であり、完全なセットアップではない。ファイル操作、レジストリ、ショートカット、実行中アプリの扱い、パス検証も移植対象となる。

起動部を事前ビルドして配布し、生成時に定義・データを追記し、アイコン・バージョン・実行権限の PE リソースを更新する構成なら、利用者に C++ ビルド環境を要求する必要はない。Windows と Wine の動作は別途確認する。

### B. WPF を維持し、bundle 内ファイルを配布データから参照する

現在の画面と直接起動を保つ中間案。.NET bundle とインストール対象にハッシュが一致する DLL があれば、7z 内に再格納せず、インストール時に bundle 内の元データを復元する。

既存の `runtimeDirectory` 指定を有効にするだけでは実現しない。現在の共有機構はディスク上の DLL を読む設計で、単一 EXE 内の管理 DLL はその場所に存在しない。bundle の範囲・圧縮情報を読む仕組みと、新しい共有参照が必要。同じ名前の DLL でも内容が違えば共用せず、ハッシュ一致を条件にする。

現物の bundle v6.0 を解析し、各ファイルを復元して SHA-256 を比較したところ、配布フォルダーの 377 ファイル、126,857,052 バイト（120.98 MiB、圧縮前データの 87.65%）が完全に一致した。残りは 59 ファイル、17,878,079 バイト（17.05 MiB）。この残りだけを 7-Zip 24.08 の LZMA2 レベル 9 で圧縮すると 5,131,854 バイト（4.89 MiB）となった。

したがって、**現行 bundle 61.17 MiB＋固有データ 4.89 MiB＝約 66.06 MiB** が構成上の参考値になる。現行 102.91 MiB より約 35.8% 小さい。共有参照用の新しい manifest、追加コード、生成アイコン等を含める前の値であり、完成したインストーラーの実測値ではない。HSIS 自身の配布データでの結果で、別アプリではランタイムの種類・バージョンに応じて一致する量が変わる。

実装は、bundle の解析を生成側で行い、実行ファイル内の offset・格納長・元の長さ・圧縮方式・SHA-256 を manifest に記録する構成が考えられる。実行側は指定範囲のストリームと DeflateStream で復元する。未知の bundle 形式やハッシュが一致しないファイルは通常の配布データへ格納する。厳密な範囲・長さ・内容検証を維持し、WPF 起動前に全ランタイムを展開する方式へ戻す必要はない。

この案でも固定のセットアップ bundle 約 61.17 MiB は残る。.NET の bundle 形式への追従と検証の負担も加わる。構成サイズの計算は [bundle-projection.json](bundle-projection.json) に保存した。

### C. WPF の構成を保ち、不要物と余分な I/O を減らす

小さく着手できる案。セットアップ専用プロジェクトを分け、生成用 UI、NSI 解析、コンパイル、アイコン抽出などを配布用実行部から除く。とくに `System.Drawing.Common` はビルド時のアイコン取得に使われ、実行部の削減候補になる。

日本語のみの製品とするなら、他言語の衛星リソースを発行対象から外す。今回の配布フォルダーの衛星リソースは全言語合計 8,784,456 バイト（8.38 MiB、圧縮前）。日本語分は保持するため全量が削減額ではなく、最終 EXE の削減量はさらに小さい。PDB は全体でも 80,156 バイト、Template は 177,742 バイトで、主な容量要因ではない。Template はインストール後の生成機能に必要。

展開経路は現在「EXE 内のデータ → 一時 7z → 一時フォルダーへ全展開 → 最終配置先へコピー」。圧縮データを EXE 内の範囲から直接読み、配置先と同一ボリュームの一時フォルダーへ展開後に移動する構成なら、余分な書き込みと全量コピーを減らせる。事前のパス検証、リンク拒否、破損・中断・既存インストールの扱いを維持する。

## 圧縮と展開方式

現行は 7z / LZMA2、圧縮レベル 9。生成は標準 tar、または `HSIS_7ZIP_PATH` で指定した 7-Zip を利用する。展開の既定実装は SharpCompress で、同環境変数を指定した場合だけ 7-Zip を使用する。README の「展開は標準 tar」という説明は現在のコードと一致していない。

圧縮レベルを下げても、展開が必ず速くなるとは限らない。圧縮方法だけでなくデコーダとディスク I/O を分けて測る。今回はサイズ最小を優先するため、LZMA2 を基本候補とし、デコーダの高速化と中間コピー削減を先に評価する。Zstandard は速度をさらに優先する別候補として、デコーダを含むサイズと実際の対象ファイルで比較する。

### 今回の展開測定

同じ 437 ファイルを収める 7z を、毎回新しい出力フォルダーへ展開した。SharpCompress は現在の `Hsis.Core.SevenZip.ExtractAsync` を使用し、`HSIS_7ZIP_PATH` を解除。ネイティブ側は 7-Zip 24.08 x64 を利用した。

| 圧縮レベル | 7z 本体 | SharpCompress 0.49.1 | 7-Zip ネイティブ |
|---|---:|---:|---:|
| 9（現行） | 41.69 MiB | 16.54 秒（最終確認） | 2.17 / 2.21 秒 |
| 7 | 42.27 MiB | 16.79 秒 | 2.11 秒 |
| 5 | 42.82 MiB | 16.85 秒 | 1.41 秒 |

レベル 9 の SharpCompress は全測定で 16.29〜19.35 秒。最終の 16.54 秒は他の圧縮計測が終わってから再確認した値。現行 archive は辞書 64 MiB、solid block 1 個だった。

現行の同じ archive でもデコーダを変えると、この環境では約 7.5 倍の差があった。サイズ最小を優先するならレベル 9 を保ち、ネイティブデコーダと余分な I/O の削減を評価するのが有力。今回の単回測定では、レベル 5 のネイティブ展開はレベル 9 より約 0.8 秒短く、圧縮データは約 1.13 MiB 大きかった。SharpCompress ではレベル変更による明確な高速化は確認できなかった。

この時間はファイル展開処理だけの測定。EXE からの archive 切り出し、UI 起動、最終配置先へのコピー、レジストリ・ショートカット・削除 EXE の作成は含まない。ネイティブ側はプロセス起動を含む。OS キャッシュを消去した測定ではなく、Windows / Wine 全環境での所要時間や、新しく組み込む SDK デコーダの速度を保証するものでもない。計 10 回の展開測定のうち初回の展開内容を基準に、追加の 9 出力を SHA-256 で照合し、すべての内容一致を確認した。数値と測定条件は [results.json](compression/results.json)、追加 9 出力の検証結果は [hash-checks.json](compression/hash-checks.json) に保存した。

過去の `artifacts/compression-benchmark/Recommendation.txt` は VideoEditor 単体の計測で、今回の HSIS データや現在のデコーダと条件が異なるため、今回のサイズ・時間として流用しない。

## 判断

生成するインストーラーの最小化を第一にするなら A。セットアップ用の .NET / WPF をなくす効果は、対象アプリとのランタイム一致に依存しない。ネイティブ UI の実装・検証が必要になる。

現在の WPF Fluent の画面を維持する条件なら B が有力。HSIS 自身では約 66 MiB という構成上の目安を確認できた。C の不要物除外と I/O 削減を合わせて進め、残る LZMA2 データにネイティブデコーダを使う案を比較する。

どちらも画面を先に表示し、インストール開始後に配布データを展開する。セットアップと削除用実行部の共用は維持する。
